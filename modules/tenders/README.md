# 招采公告抽取（modules/tenders）

给天枢智能体应用的“商务投标助手”供数。aihot 照常采集招采信源，这个模块把这些资料交给模型抽取要素，再通过带令牌的内部接口给天枢增量拉取。天枢那边核对原话、按公司投标条件初筛。网站页面不受影响。

## 怎么工作

- **登记**：定时任务 `tenders.extract`（每 15 分钟）把打了“招标”“中标”“招标计划”标签的信源最近 30 天的资料登记进 `tender_notices`。已登记资料继续追踪输入修订（包括正文、HTML 附件和正文状态）；变化时保存新快照、清空旧抽取和失败次数并重新排队。
- **抽取**：正文抓到以后（或者发现资料两小时后还没有正文，就用标题和摘要），标题、摘要、正文里**出现关注词**的交给模型抽取。抽取内容是公告类型、项目和标包、预算、五个关键时间、资格要求（资质、业绩、人员等），每项带原话。不含关注词的记为 `skipped`，不调模型。关注词由天枢根据商务管理员维护的条件清单推过来（存在 `settings` 的 `tenders.watch` 里）。还没有关注词时只登记，不抽取。
- **模型**：步骤名叫 `tenders`（后台“模型与评测”里的“招采公告解析”，环境变量 `TENDERS_MODEL`），默认用 `LLM_*`。提示词是 `industry/prompts/tender-extract.md`。调用走 `chatJson`，有付费回执和预算熔断。服务拒绝、预算用尽或回执被占用时整批停下，下次再试，不计失败次数。
- **核对**：这里只存模型的原样输出（`backend/schema.ts` 写得宽松，格式不对的字段置空）。抽取用输入快照的 hash 标识版本，落库同时核对版本和领取时的 `seq`，旧任务不能覆盖新输入。feed 的文字、附件和结果都来自同一版快照；实时文章更新后，在下一次登记前继续提供旧版完整记录。原话核对、时间换算和初筛都在天枢做。
- **游标**：登记、输入修订、抽取完成、跳过、失败、关注词重排均在同一事务中推进 `seq`。PostgreSQL `nextval` 不随事务回滚，也不保证提交顺序；已有 worker 与 API/watch 两个写入方，因此模块用事务级 advisory lock 串行化短写事务，避免大游标先提交而漏拉小游标。模型调用不持这个锁。

## 内部接口

只认 `Authorization: Bearer <TENDERS_FEED_TOKEN>`，不认会话。access 仅放行下面三个接口及其对应方法给模块校验。令牌没配（或短于 32 位）时，这些接口和不存在一样，定时任务也不运行。

| 接口 | 用途 |
|---|---|
| `GET /api/internal/tenders/feed?after=<seq>&limit=50` | 按 `seq` 增量取资料：原文地址、标题、信源和标签、时间、文字（和交给模型的是同一份）、正文里的附件链接、状态和抽取结果。资料登记、抽取完成、跳过、失败时 `seq` 都会变大，所以同一条可能出现多次，天枢按原文地址覆盖 |
| `PUT /api/internal/tenders/watch` | 天枢推关注词 `{ keywords: string[] }`；之前因为不含关注词而跳过的资料会重新排队 |
| `GET /api/internal/tenders/status` | 各状态的条数、关注词个数、每个招采信源近 30 天的条数和最近一条的时间 |

天枢和 aihot 在同一台服务器上，天枢的容器加入 aihot 的 Docker 网络，直接访问 `http://api:3001`，这些接口不经过公网。公告文字只在公司内部的两个系统之间传递，不进公开读取层，也不在网站上展示。

## 配置

- `.env`：`TENDERS_FEED_TOKEN`（`openssl rand -hex 32`），天枢的 `AIHOT_FEED_TOKEN` 填同一个值；`TENDERS_MODEL` 可选。
- 表：`tender_notices`（`0140`–`0143`），只属于这个模块。`0143` 只增加可空的输入快照列，不改历史迁移、不在发布时批量回填。旧记录在下次登记时建立快照并重新排队（可能重新产生抽取费用）；建立快照之前 feed 暂不返回这些记录，之后以更大的 `seq` 返回。升级时 API 和 worker 都要换成新版后再恢复写入，不能混跑不使用写锁的旧版。
