# 投标商机（modules/opportunities）

商务组做“盲投”：没有前期客户跟进，靠公开招采信息找与公司业务对得上的项目。每条商机都要看得出**采购什么、限价或预算、资质和业绩要求、截止时间**。来源有两类：

- **国网**（电子商务平台 ECP、电工交易专区）：公告在列表上只有批次名（“××公司2026年第五次服务授权竞争性谈判采购”），真正采购什么写在公告文件里的需求一览表，要下载附件拆开。
- **其他招采平台**：信源里打了“招标”“招标计划”标签的资料（南网、三峡、电建、公共资源交易……），一条资料当一份公告、一个项目。打了“中标”标签的信源，以及标题是中标、成交、候选人公示、更正、终止这类的不收，只看还能投的。原来的“招标商机”频道并进了这里，旧地址 `/tenders` 跳转到 `/opportunities`。

流程：

1. **发现**：每 20 分钟看一次国网两个平台“采购公告”“招标公告”列表最前面 20 条，新的入库。其他平台的资料每 5 分钟从已采集的资料里登记最近 7 天的（正文还在抓的等两小时，没等到就用摘要）。
2. **取附件**（国网）：每 5 分钟取几份新公告的公告文件（“下载公告文件”），解析其中的 Excel（XLSX、旧版 XLS、嵌套压缩包），拆成具体项目：分标、包、子包、项目名称、采购内容、最高限价（万元 / 元 / 折扣率分开）、资质、业绩、人员要求，以及原文位置。物资招标的货物清单一行一种物资（一份几千行），按分标+包合成一条，名称用物资类别，采购内容列出物资名称。附件里的 Word 公告正文也留下（最多 3 万字），下一步抽要素用。不用 OCR，也不点“获取采购文件”（要登录、购买的那部分不碰）。
3. **筛选**：按后台“投标商机”里的**业务口径**：命中排除词的直接无关；其余每 60 个一批交给模型，判断相关 / 待确认 / 无关并写一句理由（其他平台的资料攒成一批，不逐条调用）。模型出错时先等，取到附件 6 小时后还不行就按关键词兜底：项目名命中方向关键词的记“待确认（关键词命中）”，其余无关。相同的项目文字会复用已有的模型结果，不重复花钱。
4. **抽要素**：有相关或待确认项目的公告，把公告正文交给模型抽预算、获取 / 报名 / 投标截止和开标时间、联合体、资质 / 业绩 / 人员等通用要求和标包，每项带原话；程序逐条核对原话在正文里（时间核对月日、金额核对数字），对不上的去掉。提示词沿用招采公告抽取（`industry/prompts/tender-extract.md`），格式在 `backend/details-schema.ts`。来源没写的获取截止、开标时间和采购人用抽出来的补上。
5. **推送**：推到后台配的**推送群**（每个钉钉群一个自定义机器人，加签），可以有多个。每个群自己选推哪些业务方向和来源、要不要待确认（其他平台的待确认一律不推）、实时推送和每日汇总要不要，以及**提醒人**（姓名、手机号、关注的方向）。要素抽完后（模型不行时最多等到取到附件 6 小时），一份公告里有这个群要的项目就给这个群推一条，只列它要的项目，写明项目、包、采购内容、限价或预算、资质业绩要求、时间节点、公告通用要求和链接，末尾 @ 关注这些方向的提醒人（没写方向的每条都 @）；每天 8:30 每个群再推一次汇总（过去 24 小时新发现的数量、3 天内截止的项目）。每个群的每条消息只推一次：明确失败的最多再试两次，结果不明的不重发。第一次采集时已有的存量只入库不推送；已截止的、发现已超过 48 小时的也不实时推；新加或重新启用的群只实时推那以后发现的公告。
6. **查看**：`/opportunities` 按项目列出（默认相关和待确认），可按来源、业务方向和搜索词筛选；点开是整份公告：公告要素（各包都适用的预算、时间和通用要求，可展开看原文）、对得上的项目全部字段和原文位置、其余项目的名称和包。侧栏“频道”里的“投标商机”和手机底栏的“商机”指向这里。

时间、批次、采购人、限价都照抄来源原文；“采购文件获取截止”“开标时间”不是投标截止时间，投标截止单独写。

## 采集服务（fetcher/）

国网门户有动态反爬：每次接口请求都带页面脚本生成的参数。所以不直接调接口，而是用真实浏览器（Playwright + Debian 的 Chromium）像人一样打开列表和公告、点“下载公告文件”（会弹出新窗口下载）。这部分在同一 compose 里的内部容器 `sgcc-fetcher` 里跑，worker 通过 `OPPORTUNITIES_FETCHER_URL` 带令牌调用，不对外开放端口。说明见 `fetcher/README.md`。没配采集服务时，其他平台的资料照常筛选和推送。

## 配置

- `.env`：`OPPORTUNITIES_FETCHER_URL`（内网部署为 `http://sgcc-fetcher:8000`）、`OPPORTUNITIES_FETCHER_TOKEN`（至少 24 位，compose 用它启动采集服务）。两项都填才采集国网；采集还受 `COLLECT_ENABLED` 和后台“运行开关”控制。
- 推送：安全阀 `DINGTALK_PUSH_ENABLED=true` 才发；推送群在后台“商机 → 投标商机 → 推送群”里加、改、停用、测试（改动写原因，记审计）。Webhook 和加签密钥存在库里，后台只显示 Webhook 末尾几位，审计里不记。
- 模型：后台“模型与评测”里的“投标商机”一步（`OPPORTUNITIES_MODEL`），筛选和抽要素都用它；模型调用受 `MODEL_CALLS_ENABLED` 和运行开关控制。
- 业务口径：后台“商机 → 投标商机”，每行“方向名：词、词、词”，另有排除词；保存要写原因，记审计。改了口径只影响之后筛选的公告。

## 数据

`opp_notices`（公告，含公告正文 `doc_text` 和抽出的要素 `details`）、`opp_items`（项目）、`opp_push_groups`（推送群）、`opp_pushes`（推送记录，`g<群>:notice:<公告>`、`g<群>:digest:<日期>` 各一行；删群时一起删）。`opp_notices.pushed_at` 是推送处理完的时间：要它的群都推过了，或者没有群要它。无关和没筛的项目保留 90 天，相关和待确认的一直保留。附件原文件不保存，需要时到原公告下载。
